어어# Signal α 프로젝트 기획서

> **팀 LENS** — Link · Evidence · Navigate · Signal
> 흩어진 데이터를 **연결(Link)**하고, **근거(Evidence)**를 만들고, **방향(Navigate)**을 제시해, 의미 있는 **신호(Signal)**로 전달한다.

---

## 0. 한눈에 요약

| 항목 | 내용 |
| --- | --- |
| 서비스 | 공시·리포트·대안 데이터의 투자 신호를 수집·분석해 방향 일치도와 근거를 제공하는 멀티에이전트 AI 서비스 |
| 핵심 원칙 | 매수·매도 추천 없음. 데이터 방향 일치도와 근거만 제공 |
| 대상 사용자 | 공시를 열람하지만 해석이 어려운 성장형 액티브 투자자 (주 타겟: 30대) |
| 구조 | 수집(Collector) → 분석(Analyzer) → 통합(Aggregator) → 종합 판단 → 대시보드 |
| 팀 | 5명 (성진 · 은진 · 광현 · 이슬 · 규태) |

## 1. 프로젝트 개요

### 1.1 기획 의도

개인 투자자는 매일 수백 건의 공시·리포트·채용공고·특허 속에서 의미 있는 신호를 스스로 찾아야 한다. 기관 투자자와 달리 개인에게는 이를 실시간 처리할 인력도 시스템도 없다.

Signal α는 공시·증권사 리포트·대안 데이터의 투자 신호를 수집·분석하고 서로 교차검증하는 멀티에이전트 AI 서비스다. 투자 판단 자체를 대신하는 것이 아니라, 판단에 활용되는 정보의 질을 높여 더 나은 결정을 지원한다.

### 1.2 서비스 정의

> 여러 출처의 투자 신호를 한 화면에 모아 **방향 일치도**와 **근거**를 제시하는, 매수·매도를 권하지 않는 투자 정보 서비스.

### 1.3 네이밍

| 키워드 | 의미 |
| --- | --- |
| Alpha (α) | 초과수익 · 선행 신호 · 정보 우위 |
| Signal α | 수많은 신호 중 의미 있는 알파만 정제한 값 |

### 1.4 타겟 사용자

| 구분 | 정의 |
| --- | --- |
| 주 타겟 | 30대 성장형 액티브 투자자. 공시를 직접 열람하지만 해석에 어려움을 느끼며, 스스로 종목을 분석하고 투자 판단을 내리는 사용자 |
| 부 타겟 | 정보 과부하를 경험하는 투자 입문자. 데이터는 많으나 무엇을 기준으로 판단해야 할지 모르는 사용자 |

## 2. 시장 환경과 차별화

### 2.1 경쟁 환경

AI 기반 투자 정보 서비스는 이미 다수 존재한다. 증권사(토스·한국투자·우리투자 등)는 MTS에 AI 종목 분석·뉴스 요약을 탑재했고, 핀테크 앱(알파스퀘어·씽크풀 등)도 AI 종목 추천을 제공한다.

다만 이들 서비스는 두 가지 공통점을 가진다. 첫째, 대부분 **매수·매도 신호 제공**에 집중한다. 둘째, **공식 데이터(공시·뉴스·리포트)** 중심이다.

### 2.2 Signal α의 차별점

| 차별점 | 내용 |
| --- | --- |
| 매매 추천 대신 방향 일치도 | "사라/팔아라"가 아니라 "여러 소스가 같은 방향을 가리킨다"만 제시. 규제 안전 + 판단 주권 존중 |
| 대안 데이터의 선행 결합 | 채용·특허·검색 트렌드를 선행 지표로 묶어 공식 데이터와 교차검증. 경쟁 서비스 대부분이 다루지 않는 영역 |
| 선행성 가중 종합 | 선행성이 강한 데이터에 높은 가중치 부여. "변화는 먼저 나타나는 곳에서 시작된다"는 가설을 로직에 직접 반영 |
| 토론 방식 종합 | 긍정 AI·주의 AI가 근거를 제시하고 심판 AI가 방향 일치도를 정량화 |
| 근거 추적성 | 모든 신호에 원문 링크·핵심 근거 연결. AI 판단의 블랙박스를 제거 |
| Signal Journal | 사용자의 투자 판단 기록을 축적해 패턴 복기 지원 |

> **발표 대응**: "경쟁사가 없다"가 아니라 "경쟁사는 많지만 접근이 다르다"로 포지셔닝한다. 경쟁사는 매매를 추천하고 공식 데이터만 쓰지만, Signal α는 매매를 추천하지 않고 대안 데이터를 선행 지표로 결합하며 근거를 추적 가능하게 한다.

## 3. 서비스 구조

### 3.1 단계 분리 원칙

| 단계 | 역할 | LLM |
| --- | --- | --- |
| **수집 (Collector)** | 외부 소스에서 데이터를 수집하여 원본 그대로 저장 | 없음 |
| **분석 (Analyzer)** | 저장된 원본을 소스별로 분석하여 개별 신호 산출 | 있음 (`Price_Analyzer` 제외) |
| **통합 (Aggregator)** | 분석 신호를 묶어 종합 판단 | 있음 |

수집·분석·통합을 분리함으로써 AI 호출 비용을 절감하고, 수집 실패가 분석으로 전파되는 구조적 문제를 방지한다. 분석기는 외부 API를 직접 호출하지 않고 DB만 읽는다.

### 3.2 전체 흐름

```
수집 (Collector)
  6개 소스에서 원본 수집 → *_raw 테이블 (processed=false)
        ↓
분석 (Analyzer)
  소스별 개별 분석 → 각 소스 signal 산출
        ↓
통합 (Aggregator)
  ① 대안 3종 통합 (Alt_Aggregator)
  ② 전체 소스 종합 판단 (Debate_Aggregator)
        ↓
대시보드
  방향 일치도 · 근거 · 원문 링크
```

기본 처리 주기는 1일 1회 배치이며, 장중 고임팩트 공시 감지 시 해당 항목만 즉시 분석하여 종합 점수를 재산출한다.

### 3.3 대상 종목

파일럿 단계에서 대형주 소수로 시작하며, 구조는 종목 추가가 가능하도록 파라미터화한다.

## 4. 수집 단계 (Collector)

### 4.1 공통 스펙

| 규약 | 내용 |
| --- | --- |
| LLM | 호출하지 않는다 |
| 처리 범위 | 외부 소스에서 원본 데이터만 수집·저장. 가공·분석은 하지 않는다 |
| 저장 형식 | `*_raw` 테이블에 원본 저장. `processed = false` 플래그 설정 |
| 우선순위 태깅 | 즉시 처리는 `immediate`, 일반은 `batch` |
| 실패 격리 | 특정 소스 수집 실패는 해당 소스에만 국한, 다른 모듈로 전파 안 됨 |
| 인터페이스 | 공통 베이스 인터페이스 상속 |

### 4.2 소스별 수집 기간 차등화

데이터마다 변화 속도가 다르므로 수집 기간과 비교 기준을 다르게 설계한다. 획일적 기간은 노이즈를 유발한다.

| 소스 | 변화 주기 | 수집 기간 | 비교 기준 | 설계 이유 |
| --- | --- | --- | --- | --- |
| 공시 (DART) | 수시 | 최근 90일 | 건별 즉시 | 고임팩트 공시는 발생 즉시 처리 |
| 리포트 | 분기 집중 | 최근 90일 | 직전 분기 | 컨센서스 반영 기간 |
| 채용 (Hiring) | 주~월 | 최근 90일 | 직전 30일 vs 그 전 60일 | 채용 공고 게시 주기와 분기 사업 확장 반영 |
| 특허 (Patent) | 분기~년 | 최근 180일 | 직전 분기 vs 전년 동분기 | 출원-공개 시차가 커 장기간 관찰 필요 |
| 검색 (DataLab) | 일~주 | 최근 30일 | 직전 7일 vs 그 전 21일 | 검색량은 즉각 반응, 짧게 봐야 급등 포착 |
| 주가 (Price) | 실시간 | 최근 120영업일 | 이동평균·추세 | 기술적 지표 산출에 필요한 최소 기간 |

### 4.3 수집기 명세 통합표

| 항목 | C-1 `Dart` | C-2 `Report` | C-3 `Hiring` | C-4 `Patent` | C-5 `DataLab` | C-6 `Price` |
| --- | --- | --- | --- | --- | --- | --- |
| 저장 테이블 | `dart_raw` | `report_raw` | `hiring_raw` | `patent_raw` | `datalab_raw` | `price_raw` |
| 데이터 소스 | DART OpenAPI | 네이버 증권 + PDF | 사람인 | KIPRIS OpenAPI | 네이버 DataLab API | 키움증권 API |
| 수집 방식 | REST API | 크롤링 + PDF 파싱 | 크롤링 | API 호출 | API 호출 | REST API |
| 수집 기간 | 90일 + 즉시 | 90일 | 90일 | 180일 | 30일 | 120영업일 |
| 우선순위 | 고임팩트 `immediate` / 그 외 `batch` | `batch` | `batch` | `batch` | `batch` | `batch` |
| 운영 제약 | LLM 없음 | 원문 로컬 처리 (Known Issue) | IP 차단 대비 (Known Issue) | — | 정책 변경 시 대체 | 결측·정렬 보장, 7일 초과 stale 표시 |
| 담당 | 성진 | 은진 | 광현 | 이슬 | 이슬 | 규태 |

## 5. 분석 단계 (Analyzer)

### 5.1 핵심 컨벤션

> **규칙 1.** 수치는 LLM이 생성하지 않는다. DB에서 꺼내 템플릿에 삽입하고, LLM은 문장만 생성한다.
> **규칙 2.** 모든 LLM 출력은 검증 함수를 통과한 후에만 프론트엔드로 전달된다.
> **규칙 3.** 분석기는 외부 API를 직접 호출하지 않고 DB(`*_raw`)만 읽는다.

### 5.2 공식 데이터 분석기

| 항목 | A-1 `Dart_Analyzer` | A-2 `Report_Analyzer` |
| --- | --- | --- |
| 역할 | 공시 임팩트 분석 → `dart_signal` | 리포트 의견·목표가 추출 → `report_signal` |
| 입력 | `dart_raw` | `report_raw` |
| 처리 | 고임팩트 즉시 / 저임팩트 배치 | 배치 전용 |
| 핵심 로직 | ① Few-shot 방향 일관성 ② 정정공시 반전 ③ BEAT/MISS 분류 | ① 텍스트→청크→BGE-M3 임베딩→pgvector→RAG ② 컨센서스 목표가 괴리율 ③ 3개월 목표가 추이 ④ 갭 25%↑ → conflict |
| 출력 | `score` `signal` `top_disclosures` `earnings_surprise` `summary` | `score` `signal` `avg_target` `upside_pct` `target_trend` `conflict_detected` `opinions` |
| 사용 모델 | Gemini 3 Flash | BGE-M3 (검색) + Gemini 3 Flash (추출) |
| 담당 | 성진 | 은진 |

### 5.3 대안 데이터 분석기 (구조 분리)

대안 데이터는 채용·특허·검색 3종을 **각각 독립 분석**한 뒤, 별도 통합기가 묶는 구조다. 분석과 통합의 책임을 분리한다.

```
Hiring_Analyzer   → hiring_signal   ┐
Patent_Analyzer   → patent_signal   ├→ Alt_Aggregator → alt_signal
DataLab_Analyzer  → datalab_signal  ┘
```

| 항목 | A-3a `Hiring_Analyzer` | A-3b `Patent_Analyzer` | A-3c `DataLab_Analyzer` |
| --- | --- | --- | --- |
| 입력 | `hiring_raw` | `patent_raw` | `datalab_raw` |
| 핵심 로직 | 직군 키워드 분류 → 변화율 산출 | 기술 카테고리 분류 → 신규 카테고리 = 피봇 징후 | 검색량 급등(50%↑) 감지 |
| 출력 | `hiring_signal` | `patent_signal` | `datalab_signal` |
| 사용 모델 | Flash-Lite (분류) | Flash-Lite (분류) | 룰 기반 (급등 판정) |

**A-3 `Alt_Aggregator`** — 3개 signal을 통합해 단일 `alt_signal` 산출. 순수 통합 로직만 담당하며, 개별 분석은 하지 않는다. 채용·특허·검색이 동시에 같은 방향을 가리킬 때 신뢰도를 높인다.

| 항목 | 내용 |
| --- | --- |
| 입력 | `hiring_signal` · `patent_signal` · `datalab_signal` |
| 출력 | `score` `signal` `hiring_summary` `patent_summary` `datalab_summary` `cross_signal` |
| 사용 모델 | Gemini 3 Flash (통합 요약) |
| 담당 | 이슬 (통합 책임) · 광현 (채용 분석) |

### 5.4 A-5 `Price_Analyzer`

주가 수집기(C-6)가 적재한 `ohlcv_data`를 읽어, 다른 소스와 동일한 형식(방향 + 점수 + 근거)으로 변환한다. LLM 미사용, 전부 결정적 룰.

**포지셔닝** — Price는 선행 신호가 아니다. 다른 소스의 선행 신호를 **시장이 이미 반영했는지 검증**하는 역할이다. 선행 신호가 떴는데 주가가 안 움직였다면 기회 신호로 해석될 수 있다.

| 항목 | 내용 |
| --- | --- |
| 입력 | `price_raw` (ohlcv_data) — DB만 읽음 |
| LLM | 미사용. 결정적 룰 |
| 지표 | 이동평균 5/20/60, 골든/데드크로스, RSI(14), 거래량 z-score, 외인·기관 연속 순매수, 20일 변동성 |
| 점수 규칙 | 추세(±0.45) + 모멘텀 RSI(±0.1) + 수급(±0.35) → [-1,+1] 클램프. 추세·수급 강하게 충돌 시 mixed |
| risk_flags | overbought / oversold / high_volatility / volume_spike / stale_data / insufficient_history |
| 출력 | `signal` `score` `risk_flags` `indicators` `summary` |
| 담당 | 규태 |

> 0~100 점수 변환은 통합(D-1) 단계 책임으로 남긴다. 점수 정규화를 한 곳에 모아 일관성을 유지한다.

## 6. 통합 단계 (Aggregator) — `Debate_Aggregator`

팀원 5명이 각기 다른 방식으로 종합 로직을 구현하고 백테스팅으로 정확도를 비교한다. 5개 방식을 앙상블하여 최종 점수를 산출한다.

### 6.1 구현 방식 5가지 (1인 1방식)

| 방식 | 설명 | 담당 |
| --- | --- | --- |
| D-1 룰베이스 | 가중 평균 + 조건 보정. 비교 기준점(Baseline) | 성진 |
| D-2 단일 AI 판단 | 분석 신호를 하나의 LLM에 투입해 판단 | 규태 |
| D-3 멀티 페르소나 토론 | 긍정 AI → 주의 AI → 심판 AI 순차 토론 | 광현 |
| D-4 선행성 가중 | 선행성 강한 소스일수록 높은 가중치 부여 후 합산 | 은진 |
| D-5 멀티 AI 투표 | 서로 다른 제공사 모델의 독립 판단 → 다수결/가중 투표 | 이슬 |

### 6.2 D-4 선행성 가중 — 가중치 설계

선행성이 강한 데이터일수록 높은 가중치를 부여한다. "변화는 채용·특허처럼 선행 지표에서 먼저 나타나며, 주가·리포트는 이를 뒤늦게 반영한다"는 가설을 직접 구현한 방식이다.

| 소스 | 선행성 | 가중치(초안) |
| --- | --- | --- |
| 채용 | 가장 선행 | 0.30 |
| 특허 | 선행 | 0.25 |
| 검색 트렌드 | 선행 | 0.20 |
| 공시 | 반응 | 0.15 |
| 리포트 | 후행 | 0.10 |
| 주가(Price) | 검증용 | 0.00 (가중 제외) |

> 가중치는 초안이며 백테스팅 결과로 조정한다.

### 6.3 토론 구조

| 역할 | 정의 |
| --- | --- |
| 긍정 AI (Bull) | 긍정 방향 사실만 정리. 주가·매매 판단 제외 |
| 주의 AI (Bear) | 리포트 충돌, 트렌드 약화, 표본 부족 등 주의 사실 정리 |
| 심판 AI (Judge) | 양측 근거 종합 → 방향 일치 여부와 최종 신뢰도 결정 |

### 6.4 분석 실패 시 처리 정책

| 실패 수 | 처리 | 신뢰도 상한 |
| --- | --- | --- |
| 0개 | 전체 분석 제공 | 제한 없음 |
| 1개 | 분석 제공 + CAUTION 배너 | 제한 없음 |
| 2개 | 분석 제공 + WARNING 배너 | 40점 상한 |
| 3개 전부 | 분석 미제공 + 재시도 버튼 | — |

**출력 필드** — `score` `confidence` `signal` `source_agreement` `bull_argument` `bear_argument` `summary` `needs_review`

## 7. 화면·시각화 설계
