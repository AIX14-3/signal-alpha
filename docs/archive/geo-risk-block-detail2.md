# 지정학 리스크 차단(Kill-Switch) 상세 문서 — 단독 라인

> 이 문서는 signal-alpha 홈페이지를 "지정학 리스크 발생 시 일시 차단"하는 기능의
> **차단 동작 그 자체**만 깊게 다룹니다. (뉴스 감지 에이전트의 수집/판정 내부 구현은 별도 문서)
>
> ⚠️ **설계 원칙: 단독(Standalone) 베이스라인.** 이 통제 기능은 **기존 테이블·기존 코드를 재사용하지 않는
> 독립 코드 라인**으로 만듭니다. 전용 테이블(`guard_*`)·전용 API(`/api/guard/*`)·전용 패키지
> (`app/homepage_guard/`)로 구성하며, 기존 분석/신호 코드와 import·테이블이 겹치지 않습니다.
> 기존 컬렉터/워커 프로세스 위에서 **실행(호스팅)** 하는 것만 공유합니다.
> (뉴스/LLM 라인 상세: `docs/geo-risk-news-agent-llm.md`)

---

## 1. 왜 차단이 필요한가 (문제 정의)

signal-alpha의 리포트는 DART·증권사 리포트·대체데이터·시세를 종합해 "BUY/SELL/HOLD" 신호를 냅니다.
하지만 이 신호는 **전쟁·분쟁 같은 지정학 충격을 입력으로 받지 않습니다.**

그래서 큰 사건이 터지면 신호와 실제 주가가 어긋납니다.

| 상황 | 실제 주가 | 우리 리포트 | 결과 |
|------|-----------|-------------|------|
| 전쟁 발발 / 확전 | 급락 | 평소처럼 BUY 가능 | 사용자가 BUY 믿고 손실 |
| 휴전 / 종전 | 급등 | 평소처럼 SELL 가능 | 사용자가 SELL 믿고 기회 손실 |

→ 모델이 신뢰할 수 없는 구간에서는 **잘못된 신호를 내보내느니, 잠시 멈추고 안내하는 편이 안전**합니다.
이것이 "차단(Kill-Switch)"의 목적입니다. 모델을 고치는 게 아니라, **위험 구간에 서비스를 보호**하는 장치입니다.

핵심 원칙: **"확신이 없으면 차단한다(fail-safe)."** 의심스러우면 신호를 내보내지 않는 쪽으로 기운다.

## 2. 차단의 작동 원리 (한 문장)

> **DB에 "사이트 상태(guard_site_status)"라는 값 하나를 두고, 백엔드·프론트·생성 파이프라인이 모두 그 값을
> 읽어서 동작한다. 이 값 하나만 바꾸면 전체가 즉시 반응한다.**

```
   누가 켜는가                무엇을 저장하는가              누가 읽고 반응하는가
 ┌─────────────┐          ┌──────────────────┐         ┌──────────────────────┐
 │ 관리자(수동)  │ ──set──▶ │  guard_site_status   │ ──read─▶│ ① 공개 status API     │
 │ 에이전트(자동)│          │  (DB 1행)         │         │ ② 프론트 화면          │
 └─────────────┘          │  status/scope/... │         │ ③ 리포트 생성 파이프라인 │
                          └──────────────────┘         └──────────────────────┘
```

- **단일 진실원천(single source of truth)**: 차단 상태는 오직 이 한 곳에만 있습니다. 화면·API·파이프라인이
  각자 따로 판단하지 않고 전부 이 값을 봅니다 → 불일치(어떤 페이지는 막히고 어떤 페이지는 안 막힘)가 없습니다.
- **재시작 불필요**: 환경변수(.env)가 아니라 DB 값이므로, 서버를 껐다 켤 필요 없이 즉시 토글됩니다.

### 저장되는 값 (guard_site_status)
| 필드 | 의미 | 가능한 값 |
|------|------|-----------|
| `status` | 지금 막혀 있나? | `ok`(정상) / `blocked`(차단) |
| `scope` | 무엇을 막나? | `report_generation` / `report_view` / `whole_site` |
| `mode` | 누가 켜고 끄나? | `manual`(관리자만) / `advisory`(에이전트 추천) / `auto`(에이전트 자동) |
| `reason` | 사용자에게 보여줄 사유 | 예: "이란-미국 분쟁 속보로 리포트 신뢰도 확보 시까지 일시중단" |
| `resume_at` | 언제 재개 예상? | 시각 또는 미정(null) |
| `triggered_by` | 누가 켰나 (기록) | `admin:biop99999` / `agent:geo-risk-monitor` |

## 3. 차단 범위(scope) 3종 — 무엇을, 어디까지 막나

차단은 "전부 아니면 전무"가 아닙니다. 상황 심각도에 따라 **약하게 → 강하게** 3단계로 고를 수 있습니다.

### 3-1. `report_generation` — 리포트 생성만 중단 (가장 약함)
- **막는 것**: 새 신호 생성, 새 리포트 분석.
- **그대로 두는 것**: 홈, 검색, 이미 만들어진 리포트 조회.
- **사용자 경험**: 거의 평소와 같음. 다만 상단에 작은 배너 — *"현재 신규 분석을 일시 중단했습니다."*
- **언제 쓰나**: 리스크는 감지됐지만 아직 기존 데이터는 볼 만할 때. "새 판단만 멈춤".

```
[홈] 정상  [검색] 정상  [기존 리포트] 정상(+배너)  [새 신호 생성] ⛔ 중단
```

### 3-2. `report_view` — 리포트 조회까지 차단 (중간)
- **막는 것**: 리포트 상세 페이지(`/report/[종목]`) → "일시중단" 화면으로 대체. 새 생성도 당연히 중단.
- **그대로 두는 것**: 홈, 검색(종목을 찾을 수는 있음).
- **사용자 경험**: 종목을 눌러 리포트로 들어가면 리포트 대신 안내 화면 + 사유.
- **언제 쓰나**: 이미 만들어진 신호조차 지금 보여주면 위험할 때(오판 유도 우려).

```
[홈] 정상  [검색] 정상  [리포트 상세] ⛔ "일시중단" 화면
```

### 3-3. `whole_site` — 홈 전체 차단 (가장 강함)
- **막는 것**: 홈·검색·리포트 등 거의 모든 페이지 → 전체 "일시중단" 안내 화면.
- **예외(허용)**: `로그인`, `회원가입`, `요금제`, `관리자` 페이지(운영·결제·관리 위해 열어둠).
- **사용자 경험**: 어떤 페이지로 들어와도 "지정학 리스크로 서비스를 일시 중단합니다" 안내.
- **언제 쓰나**: 시장 전체가 비정상(대형 전쟁 발발 직후 등)이라 어떤 신호도 신뢰 불가일 때.

```
[모든 페이지] ⛔ "일시중단" 화면     예외: /login /signup /pricing /admin
```

> **단계 선택 가이드**: 약→강 순서로 `report_generation` → `report_view` → `whole_site`.
> 평소엔 가장 약한 단계로 시작하고, 사건이 커지면 관리자가 단계를 올립니다.

## 4. 발동 방식(mode) — 누가 차단을 켜고 끄나

### 4-1. `manual` (수동) — 관리자가 직접
- 관리자 콘솔의 토글로 ON/OFF. scope·reason을 직접 입력.
- 가장 단순하고 안전. 사람이 판단하므로 오탐(잘못 막힘)이 없음.

### 4-2. `advisory` (추천) — 에이전트가 제안, 사람이 결정 ★권장 기본값
- 뉴스 감시 에이전트가 위험을 감지하면 **차단을 "제안"만** 합니다(자동으로 막지 않음).
- 관리자 화면에 "차단 제안" 카드가 뜨고 → 관리자가 **승인하면 그때 차단**.
- 장점: 에이전트의 빠른 감지 + 사람의 최종 판단 → 오탐으로 사이트가 통째로 막히는 사고 방지.

### 4-3. `auto` (자동) — 에이전트가 스스로
- 위험도가 임계값을 넘으면 사람 개입 없이 즉시 차단, 해소되면 자동 해제.
- 가장 빠름. 단, 오탐 위험이 있으므로 **안전장치**가 필수(아래 6장).

```
 manual   : [관리자] ─직접 ON/OFF─▶ 차단
 advisory : [에이전트] ─제안─▶ [관리자 승인] ─▶ 차단      (권장)
 auto     : [에이전트] ─임계값 초과─▶ 차단 (자동)
```

## 5. 차단이 켜졌을 때 전체 흐름 (End-to-End)

이란-미국 전쟁 발발 시나리오로 따라가 봅니다. (mode=advisory, scope를 whole_site로 올리는 예)

```
1) [감지]  에이전트가 "이란-미국 무력충돌 확전" 뉴스 감지 → 위험도 92/100
2) [제안]  advisory 모드 → 관리자 화면에 "전체 차단 제안" 카드 표시 (자동 차단 안 함)
3) [결정]  관리자가 카드 승인 → guard_site_status 를 status=blocked, scope=whole_site,
           reason="이란-미국 분쟁 속보로 리포트 신뢰도 확보 시까지 일시중단" 으로 설정
4) [전파]  · 전용 공개 API 가 즉시 blocked 응답
           · 프론트가 폴링(30~60초)으로 감지 → 전체 페이지를 "일시중단" 화면으로 교체
5) [사용자] 홈/리포트에 접속하면 사유와 함께 "일시중단" 안내를 봄
6) [해제]  상황 진정 → 관리자가 ok 로 해제(또는 auto 모드면 위험도 하락 시 자동 해제)
           → 프론트 폴링이 ok 감지 → 화면 원복
```

### 전파 경로 (차단 값이 실제로 효력을 내는 지점) — 모두 단독 라인
차단은 **사용자에게 보이는 것(serving/프론트 edge)** 에서 통제 라인 단독으로 enforce 합니다.
기존 신호/분석 코드를 건드리지 않습니다.

1. **전용 공개 API** `GET /api/guard/status` (통제 라인 전용 라우터)
   - 비로그인 포함 누구나 호출. 프론트가 이 값만 폴링해서 화면을 바꿉니다. (기존 신호 API와 무관)
2. **프론트엔드 화면**
   - 전용 통제 게이트(독립 컴포넌트/스토어)가 scope에 따라: 배너만 / 리포트만 차단 / 전체 차단 화면을 렌더.
   - 리포트 페이지 진입 시에도 이 전용 API를 보고 차단 화면으로 대체 → **이미 생성된 위험 신호의 "노출"을 막음**.

> **참고 — 리포트 "생성" 자체를 멈추고 싶을 때:** 기존 생성 파이프라인(aggregation)을 멈추려면 그 코드를
> 건드려야 하므로 **단독 라인 원칙과 충돌**합니다. 기본 설계는 **"노출 차단"으로 충분**(차단 중엔 새 신호가
> 사용자에게 안 보임). 생성까지 끊는 것이 꼭 필요하면, 통제 라인의 `guard_site_status` 를 **읽기 전용으로
> 참조하는 최소 훅** 1줄을 파이프라인에 두는 **선택적 통합**으로 분리합니다(기본은 비활성).

## 6. 안전장치 (오탐·사고 방지)

차단은 강력한 만큼, 잘못 켜지거나 안 꺼지면 그 자체가 사고입니다. 다음 장치를 둡니다.

| 위험 | 안전장치 |
|------|----------|
| 에이전트 오탐으로 전체 사이트가 막힘 | 기본은 `advisory`(사람 승인). `auto`는 scope 상한을 둠(예: 자동은 `report_generation`까지만, `whole_site`는 사람 승인 필수) |
| 차단이 켜진 채 잊혀짐 | `resume_at`(예상 재개 시각) 표시 + 관리자 대시보드에 항상 현재 차단 상태 노출 |
| 깜빡임(켜졌다 꺼졌다 반복) | `auto` 해제에 **쿨다운/최소 유지시간** 적용 → 잦은 토글 방지 |
| 관리자가 자기 페이지까지 막아 못 들어감 | `/admin`, `/login` 은 `whole_site`에서도 **항상 예외 허용** |
| 누가/언제/왜 바꿨는지 추적 불가 | 모든 변경을 **감사 로그(audit)** 에 기록(`actor`, `action`, `reason`, 시각) |
| status API 장애 시 화면 동작 | API 호출 실패 시 프론트는 **차단하지 않음(정상 노출)** 으로 처리 → 차단 기능 장애가 서비스 전체를 막지 않게 |

> 참고: 마지막 항목은 "fail-open"입니다. 차단 인프라 자체가 죽었을 때 사이트를 통째로 막아버리면
> 더 큰 장애이므로, 인프라 장애 시엔 정상 노출로 둡니다.


## 8. 자주 묻는 질문 (FAQ)

- **Q. 차단하면 데이터가 지워지나요?**
  아니요. 신호·리포트 데이터는 그대로 보존됩니다. 통제 라인은 **"사용자에게 보여주기"만 일시 중지**합니다.
  (기존 신호 테이블을 건드리지 않으므로 해제하면 즉시 원래대로 노출)

- **Q. 왜 기존 코드/테이블과 분리하나요?**
  통제 라인은 안전장치라, 기존 분석 코드와 얽히면 한쪽 변경이 다른 쪽을 깰 위험이 있습니다.
  전용 테이블(`guard_*`)·전용 API(`/api/guard/*`)·전용 패키지(`app/homepage_guard/`)로 **독립**시키면,
  통제 기능을 자유롭게 켜고/끄고/떼어낼 수 있고 기존 서비스에 영향을 주지 않습니다.

- **Q. 차단 중에도 관리자는 일할 수 있나요?**
  네. `/admin`은 항상 열려 있어 상태 확인·해제가 가능합니다.

- **Q. 종목별로 막을 수 있나요?**
  이 설계의 차단은 **사이트 전역(scope 단위)** 입니다. 종목 단위 차단은 범위 밖이며,
  필요하면 별도 확장(종목별 게이트)으로 검토합니다.

- **Q. 자동(auto)이 위험하지 않나요?**
  그래서 기본은 `advisory`(사람 승인)이고, `auto`도 scope 상한·쿨다운으로 피해를 제한합니다.
