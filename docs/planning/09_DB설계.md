# 09. DB 설계

> Signal α 하위 문서 | 상위: [00_메인_기획서.md](00_메인_기획서.md)
> 노션 "DB 설계 초안"을 **실제 마이그레이션 베이스라인**(`database/migrations/001~013`, PR #91 재구성) 기준으로 정합화했다. 스키마 상세는 [`database/README.md`](../../database/README.md)와 [`database/erd/signal_alpha_core_erd.md`](../../database/erd/signal_alpha_core_erd.md)가 사실 기준이다.

## 0. 핵심 요약

Signal α의 DB는 기존 팀원 ERD(서비스 운영 구조)에 **데이터 수집·정규화·Agent 분석 구조**를 병합한 설계이며, 현재 마이그레이션 베이스라인으로 전부 구현되어 있다.

| 영역 | 역할 | 출처 |
| --- | --- | --- |
| Market | 종목, 주가, 재무 데이터 관리 | 기존 ERD |
| Analysis | 분석 요청, 점수, Agent 결과 관리 | 기존 ERD |
| User / Billing | 사용자, 구독, 관심종목 관리 | 기존 ERD |
| Admin | 관리자 계정 및 세션 관리 | 기존 ERD |
| Collection / Raw | 외부 API·크롤링 원본 데이터 저장 | 병합 추가 |
| Processing / Normalization | 수집 데이터를 공통 시그널 구조로 변환 | 병합 추가 |
| Signal Pipeline / Final Signal | 방향성 판단과 프론트 조회용 최종 시그널 | 병합 추가 |

> **Collector가 데이터를 수집하고, Normalizer가 공통 시그널로 변환한 뒤, Agent가 분석하고, 프론트는 최종 결과인 `final_signals`를 조회하는 구조다.**

---

## 1. 전체 데이터 흐름

```
[1] Collector 실행
[2] raw_documents에 원본 공통 메타데이터 저장
[3] Collector별 detail 테이블 저장
[4] processing_queue에 정규화 작업 등록
[5] Normalizer 실행
[6] source_documents 생성
[7] signal_events 생성
[8] signal_metrics 생성
[9] processing_queue에 Agent 분석 작업 등록
[10] Agent 분석 실행
[11] analysis_results / agent_results 저장
[12] Bull / Bear / Judge Debate 실행          [계획]
[13] ML Scorer 보정                            [계획]
[14] final_signals 저장
[15] Frontend에서 final_signals 조회
```

---

## 2. 설계 핵심 원칙

### 2-1. Collector는 LLM을 호출하지 않는다

Collector의 책임은 4가지뿐이다: ① 외부 API/크롤링 수집 ② `raw_documents` 저장 ③ detail 테이블 저장 ④ `processing_queue`에 NORMALIZE 작업 등록.

수집과 분석을 분리하지 않으면 유지보수(수집 실패 vs 분석 실패 구분 불가)·비용(수집마다 LLM 호출)·재처리(분석 로직만 교체 불가)·테스트가 모두 어려워진다.

### 2-2. Raw 데이터와 분석용 데이터를 분리한다

원본은 Raw 계층(`raw_documents` + `dart/report/hiring/patent/datalab_raw_details`)에 보존하고, Normalizer가 분석 가능한 형태(`source_documents`·`signal_events`·`signal_metrics`)로 변환한다.

### 2-3. Agent는 Raw 테이블을 직접 조회하지 않는다

- Agent가 조회: `source_documents` · `signal_events` · `signal_metrics` · `report_chunks`
- Agent가 저장: `analysis_results` · `agent_results` · `final_signals`

### 2-4. Frontend는 final_signals 중심으로 조회한다

기본 조회는 `final_signals` 하나. 상세 근거가 필요할 때만 `source_documents`·`signal_events`·`signal_metrics`를 추가 조회한다.

## 3. Zone별 테이블 구조 (마이그레이션 베이스라인 기준)

마이그레이션 파일 매핑: `001_extensions` → `002_market` → `003_collection_core` → `004~006_collection_(dart·datalab·hiring)` → `007_processing` → `008/010_users_billing` → `009_analysis` → `011_admin` → `012_triggers` → `013_legacy_report_mvp`.

### Zone A. Market (`002_market.sql`)

| 테이블 | 역할 |
| --- | --- |
| stocks | 종목 기준 테이블. `is_target` 스위치로 수집 대상 결정 |
| ohlcv_data | 주가, 거래량, 외국인/기관 순매수 |
| price_snapshots | 장중 시점별 스냅샷 (키움 REST 폴링 데몬 적재) |
| fundamentals | 재무 기본 지표 |

### Zone B. Collection / Raw (`003~006`)

| 테이블 | 역할 |
| --- | --- |
| raw_documents | 모든 수집 원본의 공통 메타데이터 (공통 입구, `source_hash`로 중복 방지) |
| dart_raw_details / report_raw_details / hiring_raw_details / patent_raw_details / datalab_raw_details | 소스별 상세 |
| report_chunks | 리포트 RAG용 청크 + 임베딩 (`VECTOR(1024)`) |
| collector_runs | 수집 세션 단위 실행 로그 |
| dart_corp_codes · dart_collection_states | DART corp_code 매핑·수집 상태 |
| datalab_categories · datalab_category_keywords · datalab_category_stocks | 검색 카테고리-종목 매핑 |
| hiring_baseline | 채용 비교 기준선 |

### Zone C. Processing / Normalization (`007_processing.sql`)

| 테이블 | 역할 |
| --- | --- |
| processing_queue | 수집·정규화·분석 작업 상태 관리 |
| source_documents | 분석·프론트 공용 근거 문서 |
| signal_events | 공통 시그널 이벤트 (source_type × event_type) |
| signal_metrics | 시그널 연결 수치 지표 (LLM 숫자 오류 방지) |
| validation_logs | 검증 로그 |

`signal_events` 공통화 예시:

| source_type | event_type | 의미 |
| --- | --- | --- |
| DART | SUPPLY_CONTRACT / EARNINGS_RELEASE / SHARE_BUYBACK | 공급계약 / 실적 발표 / 자사주 매입 |
| REPORT | TARGET_PRICE_UP / TARGET_PRICE_DOWN / OPINION_UPGRADE | 목표주가 상·하향 / 투자의견 상향 |
| HIRING | HIRING_SPIKE / HIRING_DROP | 채용공고 급증 / 감소 |
| PATENT | NEW_PATENT_CATEGORY / PATENT_SPIKE | 신규 기술 카테고리 출원 / 출원 증가 |
| DATALAB | SEARCH_VOLUME_SPIKE / SEARCH_VOLUME_DROP | 검색량 급증 / 감소 |

`signal_metrics` 지표 예시: target_price · previous_target_price · upside_pct · hiring_count · patent_count · search_index · search_change_pct · contract_amount · revenue_growth_pct

`processing_queue.task_type` 예시:

```
NORMALIZE_DART / NORMALIZE_REPORT / NORMALIZE_HIRING / NORMALIZE_PATENT / NORMALIZE_DATALAB
CHUNK_REPORT / EMBED_REPORT
ANALYZE_DART / ANALYZE_REPORT / ANALYZE_ALT
AGGREGATE_DEBATE / ML_SCORE / CREATE_FINAL_SIGNAL    ← 처리기는 [계획]
```

### Zone D. Analysis (`009_analysis.sql`)

| 테이블 | 역할 |
| --- | --- |
| analysis_requests | 사용자 분석 요청 기록 |
| analysis_results | 분석 요청에 대한 대표 결과 |
| quant_scores / ta_scores / ai_scores | 정량·기술적·AI 점수 |
| agent_results | Bull / Bear / Judge Agent 결과 |
| ml_scores · xgb_model_versions | ML 보정 점수·모델 버전 `[계획 단계 활용]` |
| score_history | 점수 이력 |
| backtest_results | 백테스트 결과 |
| final_signals | 프론트 조회용 최종 시그널 |

**`final_signals` 주요 컬럼 (실제 스키마)**: `final_score`(0~100) · `confidence`(내부 컬럼, 0~100) · `signal`(positive/negative/neutral/mixed) · `source_agreement`(HIGH/MEDIUM/LOW) · `warning_level`(NORMAL/CAUTION/WARNING) · `score_breakdown`(JSONB — 소스별 점수) · `summary` · `bull_point`/`bear_point` · `disclaimer`(면책 문구 기본값 강제) · `needs_review` · `run_key`/`version`/`is_current` · `min_plan_required`/`is_published`

> 초안의 소스별 개별 컬럼(dart_score, report_score, …)은 실제 스키마에서 `score_breakdown` JSONB 하나로 통합되었다. 사용자 노출 용어로는 `confidence` 대신 `consensus_score`/`alignment_rate`를 쓴다 (06 문서 용어 원칙 참조).

### Zone E. User / Billing (`008`·`010`)

users · social_accounts · portone_verifications · terms_agreements · signal_subscriptions · subscription_plans · watchlists · signal_journals · user_signal_reads

MVP에서는 필수 구현이 아니며, 분석 파이프라인 완성 후 확장한다.

### Zone F. Admin (`011_admin.sql`)

admin_accounts · admin_sessions

### Legacy (`013_legacy_report_mvp.sql`)

report_raw · report_signal — 리포트 MVP 초기 구조의 잔존 테이블. 신규 개발은 Zone B/C 구조를 사용한다.

## 5. 운영 규칙 (구현 기준 추가)

- **run_key 규칙**: 배치/즉시 실행 구분과 재실행 추적 — [`database/docs/run_key_rule.md`](../../database/docs/run_key_rule.md)
- **source_hash 규칙**: 원본 중복 수집 방지 — [`database/docs/source_hash_rule.md`](../../database/docs/source_hash_rule.md)
- **테이블 책임 구분**: [`database/docs/table_responsibility.md`](../../database/docs/table_responsibility.md)
- **배열 컬럼 한계**: `processing_queue.source_raw_ids` 등 배열 컬럼은 FK 무결성이 강제되지 않는다. MVP에서는 속도를 위해 유지하고, 모델 안정화 후 매핑 테이블로 분리한다 (`database/docs/db_design_summary.md`)
- **마이그레이션 주의**: SQL 파일은 LF 고정(`.gitattributes`) — CRLF로 바뀌면 migrate 체크섬이 깨진다

## 7. 담당자별 개발 기준

| 담당 | 기준 |
| --- | --- |
| Collector | 외부 API/크롤링 → raw_documents → detail 테이블 → NORMALIZE 큐 등록. **LLM 호출 금지** |
| Normalizer | raw_documents + detail → source_documents → signal_events → signal_metrics |
| Agent | 조회: source_documents·signal_events·signal_metrics·report_chunks / 저장: analysis_results·agent_results·final_signals. **Raw 직접 조회 금지** |
| Frontend | 기본 `final_signals` 조회, 상세 근거만 추가 조회 |
