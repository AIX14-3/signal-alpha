# Signal α 백테스팅 기능 기획안

## 1. 기능 개요

Signal α의 백테스팅은 과거 특정 시점에 생성된 시그널을 다시 재생하고, 이후 일정 기간 동안 실제 데이터 흐름이 어떻게 전개되었는지 사후 검증하는 기능이다.

이 기능은 매수·매도 추천이나 수익률 보장을 위한 도구가 아니라, **소스 방향성 일치도와 근거 품질을 검증하는 분석 도구**로 정의한다.

## 2. 기획 목적

현재 Signal α는 DART 공시, 증권사 리포트, Alternative Data를 멀티에이전트가 분석해 `consensus_score`, `alignment_rate`, `needs_review`, positive/caution evidence를 제공한다.

백테스팅 기능의 목적은 다음 질문에 답하는 것이다.

- 과거에 소스 방향성이 높게 일치했던 시그널은 이후에도 같은 방향의 데이터 흐름으로 이어졌는가?
- `needs_review`로 표시된 종목은 실제로 이후 데이터 충돌이나 리스크 이벤트가 많이 발생했는가?
- DART, Report, Alternative Data 중 어떤 소스 조합이 사후 검증에서 더 안정적인 근거를 제공했는가?
- 특정 에이전트의 판단이 반복적으로 과도하게 긍정 또는 부정으로 치우치지는 않았는가?

## 3. 핵심 원칙

백테스팅 화면과 문구는 투자 성과를 평가하거나 추천하지 않는다.

사용 가능한 표현:

- 시그널 사후 검증
- 소스 방향성 유지 여부
- 근거 확인률
- 리스크 플래그 적중 여부
- 관찰 기간 내 데이터 변화

피해야 할 표현:

- 수익률 검증
- 매수 성공률
- 추천 성과
- 승률
- 목표 수익률
- 매매 전략 검증

가격 데이터는 사용할 수 있지만, **보조 관찰 지표**로만 다룬다.

## 4. MVP 범위

### 대상 종목

초기 MVP는 기존 타깃 종목 3개로 제한한다.

- 삼성전자
- SK하이닉스
- 네이버

### 검증 기간

초기 검증 기간은 6개월에서 12개월 범위로 잡는다. 실제 과거 데이터 수급 가능성에 따라 기간을 조정한다.

### 검증 단위

백테스트의 기본 단위는 `signal_snapshot`이다.

하나의 snapshot은 다음 정보를 포함한다.

- 생성 일자
- 종목 코드
- 종목명
- 소스별 방향성
- 종합 방향성
- `consensus_score`
- `alignment_rate`
- `needs_review`
- positive evidence
- caution evidence
- 사용된 원천 데이터 시점

## 5. 데이터 구성

### 필요한 데이터

- 과거 DART 공시 데이터
- 과거 증권사 리포트 메타데이터와 요약 결과
- 과거 Alternative Data
  - 검색 트렌드
  - 채용공고
  - 특허 출원
- 과거 시그널 스냅샷
- 일별 가격 데이터
  - 종가
  - 거래량
  - 변동성
  - 시장지수 대비 변화

### 데이터 주의사항

- 미래 데이터를 과거 판단에 섞지 않는다.
- 시그널 생성 시점 이후 공개된 데이터는 입력값으로 사용하지 않는다.
- 리포트 발행일, 공시 접수일, 대체 데이터 수집일을 반드시 저장한다.
- 가격 데이터는 “결과의 참고 관찰값”으로만 사용한다.

## 6. 분석 지표

### 1. 소스 방향성 유지율

과거 시그널 생성 후 7일, 30일, 60일 동안 각 소스의 방향성이 유지되었는지 확인한다.

예:

- DART positive가 이후에도 positive 또는 neutral-positive 흐름을 유지했는가?
- Report와 Alternative Data가 시간이 지나며 충돌했는가?

### 2. 근거 확인률

positive evidence 또는 caution evidence가 이후 데이터에서 실제로 추가 확인되었는지 측정한다.

예:

- “HBM 수요 증가” 근거가 이후 리포트나 공시에서 반복 확인되었는가?
- “마진 부담” 주의 근거가 이후 실적 또는 리포트에서 재등장했는가?

### 3. `needs_review` 검증률

`needs_review: true`로 표시된 시그널이 이후에도 데이터 충돌, 리스크 플래그, 추가 확인 필요 상태로 이어졌는지 확인한다.

### 4. 리스크 플래그 발생률

시그널 생성 당시 caution evidence나 risk flag가 있었던 종목에서 이후 관련 리스크 이벤트가 발생했는지 확인한다.

### 5. 가격 반응 관찰 지표

가격 데이터는 보조 지표로만 사용한다.

- 관찰 기간 내 변동성
- 시장지수 대비 상대 변화
- 이벤트 전후 거래량 변화
- 급등락 발생 여부

이 지표는 투자 성과가 아니라 “시그널 이후 시장 반응을 관찰하는 참고값”으로 표현한다.

## 7. 사용자 화면 기획

### 백테스팅 대시보드

주요 카드:

- 총 검증 스냅샷 수
- 소스 방향성 유지율
- 근거 확인률
- `needs_review` 검증률
- 리스크 플래그 발생률

### 종목별 백테스트 상세

종목별로 다음을 보여준다.

- 시그널 생성 시점 타임라인
- 당시 소스별 방향성
- 이후 7일, 30일, 60일 관찰 결과
- 이후 확인된 공시·리포트·Alternative Data
- 가격 반응 참고 차트
- 당시 evidence와 사후 관찰 결과 비교

### 시그널 리플레이

특정 날짜를 선택하면 “그 시점에 사용 가능했던 데이터만 기준으로 생성된 시그널”을 다시 보여준다.

핵심 문구:

> 이 화면은 과거 시점의 데이터 근거를 재구성한 사후 검증 화면이며, 현재 또는 미래 투자 판단을 추천하지 않습니다.

## 8. 백엔드 설계 초안

FastAPI Main Server에 백테스팅 API를 추가한다.

### API 후보

- `POST /api/backtests/runs`
  - 백테스트 실행 요청
- `GET /api/backtests/runs/{run_id}`
  - 실행 상태 조회
- `GET /api/backtests/results`
  - 전체 결과 조회
- `GET /api/backtests/results/{stock_code}`
  - 종목별 결과 조회
- `GET /api/backtests/snapshots/{snapshot_id}`
  - 특정 과거 시그널 재생

### 주요 테이블 후보

- `signal_snapshots`
- `backtest_runs`
- `backtest_cases`
- `backtest_observations`
- `backtest_metrics`

## 9. 구현 단계

### 1단계: Mock 기반 백테스트

- 기존 mock signal 데이터를 과거 snapshot처럼 구성
- 3개 종목에 대해 가짜 관찰 결과 생성
- 프론트에서 백테스트 대시보드 화면 검증

### 2단계: 실제 과거 데이터 수집

- DART 공시 과거 데이터 확보
- 리포트 발행일 기반 메타데이터 확보
- Alternative Data 수집 가능 범위 확인
- 가격 데이터 수급 방식 결정

### 3단계: 백테스트 엔진 구현

- 과거 시점 기준으로 시그널 생성
- 관찰 기간별 결과 계산
- 데이터 누수 방지
- 결과 JSON 저장

### 4단계: 대시보드 연동

- 종목별 백테스트 요약
- 시그널 리플레이
- evidence 사후 검증 비교
- 가격 반응 참고 차트

## 10. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 투자 성과 검증으로 오해될 수 있음 | 수익률, 승률, 매수 성공률 표현 금지 |
| 미래 데이터가 과거 판단에 섞일 수 있음 | 데이터별 공개일과 수집일 저장 |
| 가격 데이터 라이선스 이슈 | 출처와 사용 범위 확인, MVP는 제한적 샘플 사용 |
| 시그널 수가 적어 통계적 의미가 약함 | MVP에서는 정량 결론보다 기능 검증 중심으로 발표 |
| LLM 판단이 재현되지 않을 수 있음 | temperature 낮게 설정, 입력 데이터와 출력 JSON 저장 |

## 11. 성공 기준

MVP 성공 기준은 다음과 같다.

- 3개 종목에 대해 과거 시그널 snapshot을 재생할 수 있다.
- 시그널 생성 시점 이후 7일, 30일, 60일 관찰 결과를 비교할 수 있다.
- `alignment_rate`, evidence, `needs_review`의 사후 검증 결과를 보여줄 수 있다.
- UI와 문서에서 투자 추천 또는 수익률 보장으로 오해될 표현을 사용하지 않는다.
- FastAPI API 응답과 프론트 mock UI가 같은 데이터 구조를 공유한다.

## 12. 발표용 한 줄 설명

백테스팅은 Signal α가 과거에 생성한 소스 방향성 시그널을 다시 재생하고, 이후 데이터 흐름과 근거 확인 여부를 비교해 시그널 품질을 검증하는 기능이다.
