# DataLab 키워드 수명(lifecycle) 설계 — 재검증 · 보존 · 기본 세트 보강

> **상태: Phase 1 설계 문서 (구현 X).** 이슈 #421의 Phase 1.
> Phase 2(알고리즘 구체화) · Phase 3(구현)는 본 문서 합의 후 진행한다.

## 1. 배경 / 문제

현재 키워드 관리는 **append-only 누적 모델**이다 (`docs/datalab-keyword-validation.md` 참조):

- **기본층(base)**: 부트스트랩 생성기가 1회 시딩한 상시 키워드. **검증 관문을 안 거침**(`validated_at` NULL).
- **이벤트층(event)**: 뉴스 파이프라인이 매일 증분 추가하는 시의성 키워드. 검색량 검증 통과분만.

한계:
1. **기존 키워드가 자동 재검증·정리되지 않는다.** 한 번 `approved`면 관리자가 끌 때까지 영구 `is_active=TRUE`. 시든(검색 안 되는) 키워드가 쌓여 수집 비용·노이즈가 누적된다.
2. **기본 세트가 무검증**이라 실제로 안 검색되는 항목이 섞일 수 있고(신규 키워드만 엄격 검증되는 비대칭), 있어야 할 기본 키워드(자회사·핵심 서비스·인물)가 누락될 수 있다.

## 2. 설계 원칙 (논의 확정)

### 원칙 1 — "신호 가치"와 "수명 정리"를 분리한다
검색량 **감소(decay) 자체가 시그널**이다(관심 식음 = 주의 근거; 제품 기획의 "긍정/주의 근거" 철학과 연계). 따라서:

- **"시들었으니 끈다"는 단순 접근을 금지**한다. 하락 추세는 분석기에 넘길 신호로 **수집·기록**한다.
- **비활성화(`is_active=FALSE`)는 신호 가치가 아니라 수집 비용·정리 차원**의 결정이며, **"오래 완전히 죽은(검색량 0이 장기 지속)"** 경우에만 적용한다.
- 비활성화는 곧 **수집 중단**이므로, 하락 중이지만 아직 검색되는 키워드는 **계속 수집**(신호 보존)하고, 진짜 휴면만 끈다.

### 원칙 2 — 삭제하지 않고 soft-delete + 이력 보존
하드 삭제(DELETE)는 하지 않는다. `is_active=FALSE` + 추세/시점 기록으로 **decay 이력을 보존**한다. DB가 누적 진실의 원천이다.

### 원칙 3 — 이벤트 키워드와 기본 키워드는 수명이 다르다
- **이벤트 키워드**: 본질적으로 한시적 → 휴면 시 보존창 후 비활성화 합리적.
- **기본 키워드**: 상시·순환적으로 조용할 수 있음 → 자동 비활성화 금지, 휴면이면 **관리자 검토 플래그**까지만.

## 3. 컴포넌트

### A. 수명 재검증 잡 (주기적)
활성 키워드 전체의 검색량을 주기적으로 재측정해 **추세를 분류·기록**한다.

- 입력: 활성 키워드(`is_active=TRUE`). 데이터: 이미 매일 수집되는 DataLab 검색량 시계열 재사용(가능 시) 또는 재조회.
- 추세 분류(상세는 Phase 2): `rising` / `sustained` / `declining` / `dormant`.
  - `dormant` = 최근 윈도에서 검색량 0이 연속 지속.
- 출력: 키워드별 `search_trend`, `last_revalidated_at` 갱신. `dormant`면 `dormant_since` 세팅(이미 있으면 유지).
- **비활성화는 보존 정책(B)에 위임** — 재검증 잡은 분류·기록만, 끄는 판단은 정책이.

### B. 보존 정책
| 키워드 종류 | 휴면(검색량 0 지속) 시 처리 |
| --- | --- |
| event | `dormant_since` 후 **보존창 경과 → soft-deactivate**(`is_active=FALSE`, 행·추세 보존) |
| base | **자동 비활성화 안 함** → `search_trend='dormant'` 플래그로 관리자 검토 대기 |

- 완전 삭제 없음. 비활성화 = 수집 중단일 뿐, 이력은 남는다.
- 재활성화 가능: 휴면 키워드가 다시 검색되면 재검증 잡이 `rising`으로 갱신, 정책상 자동/관리자 재활성화 경로 정의(Phase 2).

### C. 기본 세트 재검증 + 보강
- **재검증**: 기본 키워드(`validated_at` NULL)도 검색량 게이트에 한 번 통과시켜 실측치 기록. "원래 안 검색됨"은 강등(pending), "잠깐 조용"은 유지 — 구분 기준 Phase 2.
- **보강(gap-fill)**: 종목별 "정규 기본 세트"(자회사·핵심 제품/서비스·경영진·섹터 용어)를 LLM(+그라운딩)으로 제안 → 검증 → 누락분 병합.
- **새 종목 온보딩 자동화**: 현재는 부트스트랩 생성기 1회 수동 실행이 필요. C가 이를 표준 온보딩 절차(기본 세트 시딩 → 검증 → 매핑)로 흡수.

## 4. 스키마 초안 (Phase 3에서 마이그레이션)

`datalab_category_keywords`에 추가:

| 컬럼 | 타입 | 의미 |
| --- | --- | --- |
| `keyword_kind` | VARCHAR(10) | `base` / `event` — 보존 정책 차등의 근거 |
| `search_trend` | VARCHAR(12) | `rising`/`sustained`/`declining`/`dormant` (마지막 재검증 분류) |
| `last_revalidated_at` | TIMESTAMPTZ | 마지막 재검증 시각 |
| `dormant_since` | TIMESTAMPTZ | 휴면 진입 시점(보존창 카운트다운 기준), 회복 시 NULL |

- 백필: `validated_at IS NULL → keyword_kind='base'`, 그 외 `'event'`. 모두 `search_trend=NULL`(첫 재검증 전).
- 추세 이력 자체는 별도 테이블 없이 **기수집 검색량 시계열**을 활용 검토(중복 저장 회피). 부족하면 경량 스냅샷 테이블(Phase 2 결정).
- DB 거버넌스 준수: `IF NOT EXISTS` 금지, `updated_at` 트리거 기존 재사용, 문서 동기화(`db-governance-rules`).

## 5. 결정 필요 (open questions) — 제안 기본값 포함

| 결정 | 제안 기본값 | 근거 |
| --- | --- | --- |
| 휴면 판정(연속 검색량 0) | **event 60일 / base는 자동비활성 안 함** | 이벤트는 두 달 무검색이면 사실상 종료; 기본은 순환성 고려 |
| 재검증 주기 | **주 1회** | 검색량은 일 단위라 일별은 과함, 주 1회면 추세 포착 충분·비용 절감 |
| 추세 윈도 | 최근 7일 vs 직전 비교(스파이크 로직 재사용) | 기존 `_recent_metrics` 일관성 |
| decay→분석기 전달 | `search_trend`/coverage를 분석기가 읽어 "주의 근거"로 | 비활성화와 무관하게 신호로 노출 |
| 완전 삭제 | **안 함**(soft만) | 이력·근거 보존 |

> 위 기본값은 **제안**이며, 운영 데이터로 점진 튜닝한다(스파이크 임계 튜닝 가이드와 동일 접근).

## 6. 롤아웃 (이후 Phase)
- **Phase 2**: 추세 분류 알고리즘 확정, base 재검증의 "조용 vs 죽음" 구분 기준, gap-fill 프롬프트/검증 흐름, decay→분석기 인터페이스, (필요 시) 스냅샷 테이블 여부.
