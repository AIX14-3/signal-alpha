# PR 작성 가이드 (쉽게 정리한 버전)

> 이 문서는 Signal α의 PR 규칙을 **어려운 용어 없이** 풀어 쓴 것입니다.
> PR을 올리기 전에 이 문서 한 장만 보면 됩니다. 자세한 배경은 [`docs/backlog.md`](./backlog.md) 참고.

---

## 0. 한 줄 요약

> **"작은 단위로, 무엇을·왜 바꿨는지 적고, 투자 추천처럼 들리는 말이 없는지 확인하고 올린다."**

---

## 1. PR 올리기 전, 이 5가지만 확인하세요

1. **작게 쪼갰나?** — 한 PR은 한 가지 일만. (예: "DART 수집기"와 "대시보드 UI"를 한 PR에 섞지 않기)
2. **무엇을·왜 바꿨는지 적었나?** — 템플릿의 `설명`과 `변경 내용`만 채우면 됩니다.
3. **추천처럼 들리는 말이 없나?** — 아래 [규칙 1](#규칙-1-투자-추천처럼-들리는-말-금지-가장-중요) 확인. (가장 중요)
4. **돌려봤나?** — 로컬에서 한 번이라도 실행/테스트했는지.
5. **이슈 번호 연결했나?** — `Closes #번호` 한 줄.

## 2. Signal α만의 필수 규칙 (왜 중요한지 + 쉬운 설명)

### 규칙 1. 투자 "추천"처럼 들리는 말 금지 (가장 중요)

- **쉬운 설명**: 화면 글자, API 응답, AI 프롬프트 그 어디에도
  "사세요 / 파세요 / 추천합니다 / 오를 겁니다 / 목표가 달성 확실" 같은
  **투자를 권유하는 말**을 쓰지 않습니다.
- **왜?**: 법적으로 이런 "투자 권유"는 **자격증(투자자문업 등록)** 이 있어야 할 수 있습니다.
  우리 서비스는 추천 서비스가 아니라 **여러 데이터의 방향을 교차검증해서 보여주는 서비스**라서요.
- **어떻게?**: 금지할 표현들은 코드 여기저기에 흩어 놓지 말고,
  **한 파일에 목록으로 모아두고**(= 아래 사전의 "상수화") 코드가 자동으로 걸러내게 합니다.
- **대신 이렇게**: "이 데이터들은 같은 방향을 가리킵니다", "출처 3곳 중 2곳이 긍정적입니다" 처럼
  **사실/방향만** 전달합니다.

> 💡 처음에 어렵게 적혀 있던 규칙
> `INVESTMENT_RECOMMENDATION_PHRASES: 투자자문업 규제 대상 표현 30개 상수화`
> → **쉽게 말하면**: "투자 권유로 들리는 금지어 약 30개를 한 목록 파일에 모아두고, 코드가 자동으로 막는다."

### 규칙 2. `confidence`(확신도) 라는 단어 쓰지 않기

- **쉬운 설명**: 코드/API 필드 이름에 `confidence` 를 쓰지 않습니다.
  대신 `consensus_score`(의견 일치 점수), `alignment_rate`(방향 일치율), `source_agreement`(출처 동의) 를 씁니다.
- **왜?**: "확신도 90%"는 **"오를 거라고 확신한다"는 추천처럼** 들립니다.
  우리는 "데이터들이 얼마나 같은 방향을 보는가"만 말합니다.

### 규칙 3. 역할 섞지 않기 (수집 / 분석 / 조율 분리)

- **수집기(Collector)**: 외부에서 데이터만 가져옵니다. 방향·점수·요약을 만들지 **않습니다**.
- **분석기(Analyzer)**: 저장된 데이터만 읽어서 해석합니다. 외부 API를 직접 부르지 **않습니다**.
- **조율(Orchestrator)**: 순서만 관리합니다(수집 → 분석 → 통합).
- **왜?**: 역할이 섞이면 어디서 문제가 났는지 찾기 어렵고, 법적 책임 경계도 흐려집니다.

### 규칙 4. 저장 위치 섞지 않기

- 수집 결과 → `raw_evidence` 테이블에만
- 분석 결과 → `source_results` 테이블에만
- 통합 결과 → `signal_snapshots` 테이블에만
- **왜?**: "원본 데이터"와 "해석 결과"를 섞으면 나중에 검증·복기가 불가능합니다.

### 규칙 5. 외부 API가 실패해도 화면이 죽지 않게

- **쉬운 설명**: DART·뉴스 등 외부 호출이 실패하면, **미리 만들어 둔 가짜/대체 데이터**(fixture/mock)로
  화면이 계속 동작하게 만듭니다. 그리고 `needs_review: true`(검토 필요) 표시를 남깁니다.
- **왜?**: 발표·데모 중에 외부 API 하나 막혔다고 전체가 멈추면 안 됩니다.

## 3. 어려운 용어 → 쉬운 말 사전

| 어려운 말 | 쉬운 말 |
|---|---|
| 투자자문업 규제 대상 표현 | 법적으로 자격 없이 쓰면 안 되는 "투자 권유" 말들 |
| 상수화 (常數化) | 여기저기 흩어 쓰지 말고, **한 파일에 목록으로 모아 두기** |
| 금지 표현 필터 | 그 목록에 있는 말이 결과에 들어가면 **자동으로 막거나 고치는 코드** |
| consensus_score | 출처들이 **얼마나 같은 의견인지** 점수 (확신도 아님) |
| alignment_rate | 출처들의 **방향이 얼마나 일치하는지** 비율 |
| raw_evidence | 가공하지 않은 **원본 근거 데이터** |
| source_results | 출처별로 **해석한 결과** |
| fixture / mock | 외부 API 대신 쓰는 **미리 만든 가짜 데이터** |
| needs_review | "이 결과는 **사람이 한 번 더 봐야 함**" 표시 |

## 4. PR 제목 · 브랜치 이름 규칙

**브랜치 이름**: `종류/이슈번호-짧은설명`

- 예: `feat/issue-12-dart-collector`, `fix/issue-20-filter-bug`, `docs/issue-7-pr-guide`

**PR 제목**: `[종류] 무엇을 했는지 한 줄`

- 예: `[feat] DART 공시 수집기 추가`, `[docs] PR 작성 가이드 추가`

**종류(prefix)**

| prefix | 언제 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 코드만 정리 |
| `docs` | 문서만 변경 |
| `chore` | 설정·빌드·CI 등 자잘한 작업 |

---

## 5. 리뷰 · 머지 규칙

- PR은 **최소 1명 리뷰 승인** 후 머지합니다.
- `main`에는 **직접 push 금지**, 항상 PR로만 합니다.
- 머지는 **Squash merge**(여러 커밋을 하나로 합치기)를 기본으로 합니다.
- 리뷰어는 [규칙 1~5](#2-signal-α만의-필수-규칙-왜-중요한지--쉬운-설명)를 우선 확인합니다.
